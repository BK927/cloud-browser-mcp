# 관찰·유휴 작업 프로세스 최적화 검증

## 범위와 판단 기준

이 비교는 기존 코드와 개선 후보를 같은 Windows PC의 실제 Chrome에서 실행한
국소 실험이다. **Pi, Docker/네이티브 전체 서비스, 웹 ChatGPT의 왕복 시간 측정이 아니다.**
Pi에서 같은 절감량이 나온다고 보장하지 않으며, 운영 적용 전 별도 실측이 필요하다.

기준 소스는 `08f536200fd920835d30fb6e2555d0890434e921`이다. 당시 Pi의 배포 경로는
`ab7135e` 계열이므로 기준 소스를 현재 배포본과 동일하다고 부르지 않는다.
비교에는 같은 Python 환경, DrissionPage 버전, Chrome 실행 파일과 측정 스크립트를 사용한다.
인증 정보, 기존 브라우저 프로필, 운영 접속 경로, RAM 제한은 변경하지 않는다.
로컬 장비는 Ryzen 5 5600X(12 논리 CPU), 약 32GiB RAM, Windows 11 x86_64이며,
Python 3.13.11 / DrissionPage 4.1.1.4 / Chrome 152.0.7977.83을 사용했다.
이 로컬 시험에는 Pi의 1GiB cgroup 제한이 적용되지 않는다.

이번 후보에 남긴 변경:

- interactive/visual 관찰에서 사용하지 않는 본문 원문을 CDP 결과로 중복 전송하지 않는다.
  전체 본문의 비밀값·인증·CAPTCHA 검사는 계속 수행한다. iframe 검사와 이미지 촬영 후
  재검사도 유지한다. semantic/auto 본문과 조작 직전 안전 검사를 생략하지 않는다.
- URL 조건 대기의 중간 확인에서 전체 요소·프레임 목록을 반복 생성하지 않는다.
  URL 및 최상위 인증/차단 상태를 확인하고, 종료 시 정상 관찰로 상태와 조건을 다시 확인한다.
- 모든 작업이 정상 정리된 뒤 유예 시간이 지나면 별도 Python 브라우저 작업 프로세스를
  종료한다. 열린 작업·대기 요청·실행 요청·사용자 제어·정리 실패가 있으면 종료하지 않는다.

**제외:** 요소 좌표/스타일/이름/폼 메타데이터 캐시는 개별 효과가 입증되지 않아 제거했다.
브라우저 엔진 교체, 프로필 공유, 안전 검사 완화, 메모리 한도 증설은 하지 않았다.
semantic/auto의 원문 전송까지 없애는 확장은 접근성 캐시 지문과의 간접 의존성을
별도로 검증해야 하므로 보류했다. 이번에는 의미 본문·접근성 정보의 수집 범위를 줄이지 않는다.

## 재현 방법

`scripts/observation_benchmark.py`는 임시 프로필과 자체 로컬 fixture만 사용한다.
48개 버튼, 입력/체크 요소, 동일 출처 iframe, 긴 본문이 있는 고정 페이지에서
interactive/targeted/semantic/visual 관찰, 준비→조작→후속 관찰, 700ms URL 대기를 실행한다.
로컬 fixture 허용은 스크립트 내부의 시험 전용 우회이며 운영 네트워크 격리 검증이 아니다.

- 각 변형을 별도 프로세스로 3회, 순서는 기준→후보 / 후보→기준 / 기준→후보.
- 각 회차 1회 준비 실행 후 각 단계 5회 측정. 1024×768, JPEG 75, 출력 30000자.
- 시간 요약은 각 독립 회차 중앙값 3개의 중앙값과 범위다. 같은 프로세스 안의 반복을
  독립 실험 15회로 부풀리지 않는다.
- 두 변형 모두 대기 설정 100ms. 운영 기본값 500ms와 혼동하지 않는다.
- 시간/CPU 비교에는 `--no-cdp-meter`를 사용한다. 이때 CDP 수치 0은 비활성 표시이지
  브라우저 통신이 없다는 뜻이 아니다. CDP 호출/직렬화 크기는 별도 계측 실행으로 확인한다.
- CPU에는 Python 어댑터와 시험 서버/샘플러 부하가 포함된다. 브라우저 자식이 표본 사이에
  종료되면 CPU가 덜 집계될 수 있다. 짧은 단계와 3회 실험의 작은 차이는 개선으로 단정하지 않는다.
- RSS 합계는 공유 페이지를 중복 집계한다. Windows의 USS(전용 메모리)를 보고하고,
  제공되지 않는 PSS는 `null`로 유지한다. 표본 최고값은 순간 최고값 보장이 아니다.
  관찰 스크립트의 최고값은 준비/종료를 포함한 전체 실행 구간의 관측 가능한 프로세스 합계다.
  프로세스 조회 오류나 표본 사이 종료가 있을 수 있어 완전한 전체 물리 메모리로 단정하지 않는다.
  관찰 스크립트의 정리 성공은 남은 자식 목록과 임시 프로필 제거 확인이고, 유휴 스크립트는
  별도로 기억한 프로세스 식별자의 실제 종료까지 확인한다.

```powershell
# 두 소스에 같은 스크립트를 사용한다. 실제 경로와 Chrome 경로를 지정한다.
$env:PYTHONPATH = 'C:\path\to\baseline\src'
python scripts/observation_benchmark.py --chromium 'C:\path\to\chrome.exe' `
  --label baseline-1 --iterations 5 --no-cdp-meter --output perf-results/baseline-1.json

$env:PYTHONPATH = 'C:\path\to\candidate\src'
python scripts/observation_benchmark.py --chromium 'C:\path\to\chrome.exe' `
  --label candidate-1 --iterations 5 --no-cdp-meter --output perf-results/candidate-1.json
```

`scripts/worker_idle_benchmark.py`는 별도 서비스 객체와 실제 worker/Chrome을 두 번 열고
닫는다. 시험에서는 유예 2초, 정리 점검 간격 1초로 단축한다. 운영 기본값은 유예 30초와
점검 간격 15초다. worker 핸들이 지워져도 PID+생성 시각으로 실제 종료를 확인하며,
권한 오류를 메모리 0으로 바꾸지 않는다. 원자료에는 소스/스크립트 SHA-256을 기록한다.

```powershell
python scripts/worker_idle_benchmark.py --chromium 'C:\path\to\chrome.exe' `
  --label candidate-idle-1 --output perf-results/idle-candidate-1.json
```

## 최종 로컬 측정 결과

마지막 `validated` 자료 14개만 집계했다. 이전 후보 결과는 섞지 않았다.
[공개 수치 요약](benchmarks/observation-2026-09-16.json)에 독립 회차별 단계 요약,
메모리 표본 최고값, 유휴 주기별 측정, 별도 CDP 계측과 소스·스크립트 SHA-256을 기록했다.
14개 원자료의 기록된 소스 해시는 집계 시점의 기준·최종 후보 파일과 모두 일치한다.
아래 결과는 벤치마크 완료를 뜻하며, 전체 회귀 테스트나 CI 통과를 뜻하지 않는다.

CDP 계측을 끈 3회 실험에서 **35개 작업의 합산 CPU 중앙값은 12.391초에서
9.734초로 21.44% 감소**했다. 실행별 범위는 기준 12.234–12.906초,
후보 9.609–10.047초였다. 각 작업의 시간은 다음과 같다.
대괄호는 독립 실행 3회의 중앙값 범위이며 단위는 ms다.

|---|---:|---:|
| interactive | 136.31 [110.26–143.44] | 81.47 [79.32–106.82] |

모든 단계가 같은 폭으로 개선된 것은 아니다. semantic 시간 범위는 겹치고,
작업당 CPU 중앙값은 209.375→268.750ms로 증가해 semantic 개선을 주장하지 않는다.
URL 대기의 작업당 CPU 중앙값은 481.250→203.125ms로 57.79% 줄었다.
URL 대기 시간에는 정해진 700ms와 마지막 관찰이 포함되므로 CPU 절감과 시간 단축을
같은 의미로 해석하지 않는다.

전체 실행의 동시 표본 USS 합계 최고값은 기준 중앙값 **316.95MiB**
(311.64–322.73), 후보 **309.85MiB**(308.94–311.71)였다.
이 수치는 준비·정리까지 포함하고 범위도 일부 겹친다. **활성 작업의 RAM 절감 효과는
이 측정으로 확인하지 못했다.** RSS 합계를 실제 메모리 절감으로 대신 제시하지 않는다.

유휴 실험은 별도 프로세스로 변형별 3회, 각 2개 열기·닫기 주기를 측정했다.
기준은 유예 후 모든 6개 주기에서 작업 프로세스 1개와 USS 40.11–40.41MiB를 유지했다.
후보는 모든 주기에서 추적한 프로세스 0개, USS 0, 검사 오류 0이었다.
이는 **별도 작업 프로세스의 약 40.3MiB 회수**이며 서비스 전체 메모리가 0이라는 뜻은 아니다.

그 대가로 두 번째 열기 시간의 3회 중앙값은 **730.386→1508.352ms**, 즉
**777.966ms 증가**했다. 범위는 기준 707.968–737.406ms, 후보 1484.898–1592.809ms다.
첫 열기 중앙값은 1529.219→1492.495ms였으므로 회수 후 재시작 비용과 처음 시작하는

## 기능 회귀 검증

최종 후보의 로컬 전체 시험은 **597 passed, 9 skipped**였다(335.58초).
건너뛴 9개는 이 실행으로 검증한 항목에 포함하지 않는다. Ruff 정적 검사도 통과했다.
의존성 Starlette/AnyIO의 deprecation warning 1건은 시험 실패가 아니다.

추가 시험은 전체 본문 끝의 비밀값/사람 확인 감지, 비밀값만 있는 iframe 마스킹,
촬영 직후 비밀값 등장 시 이미지 미반환, 실제 탭 닫힘의 오류 분류를 실제 Chrome에서 확인했다.
유휴 종료의 대기 요청·사용자 제어·정리 실패 보호와 서버 종료 중의 정리/새 작업 순서도
단위 시험에 포함했다. Linux·Docker·네이티브 CI 결과는 해당 후보 커밋의 실행 기록으로
별도 확인한다. 이 문서의 로컬 결과는 Pi 운영 적용이나 전체 서비스 실측을 뜻하지 않는다.

## Pi 후속 검증 관문

배포 담당 작업이 현재 배포본의 정확한 바이트와 복구본을 확인하고 진행한다.
사용 중인 작업을 강제로 끝내지 않으며, `active_sessions == 0`과 인증/수동 제어가
없음을 먼저 확인한다. sudo가 필요하면 사용자가 비밀번호를 채팅에 보내지 않고 직접 인증한다.
기존 인증·프로필·설정·다른 MCP를 보존하고, 새 시험 인증을 임의 발급하지 않는다.

같은 1GiB 예산과 화면 조건에서 유휴 회수, 다음 열기 지연, 관찰 CPU/시간, 브라우저 전체
PSS 및 cgroup 사용량/캐시/압박/OOM을 측정한다. 이번 Windows 결과로 Pi의 절감량이나
동시 탭 수 증가를 약속하지 않는다. 실제 효과가 없거나 불리하면 해당 최적화는 보류한다.
