# Raspberry Pi Docker·네이티브 실측 결과 — 2026-09-09

기존 Docker·개선 Docker·개선 네이티브를 같은 Pi에서 각각 3회 측정했다.
**9회 모두 실행과 세션 정리를 마쳤으며 OOM kill은 없었다.** 단, 자원 보호로
거절된 요청이 있으므로 benchmark의 exit 0을 모든 도구의 성공으로 해석하지 않는다.
측정 후 기존 운영을 복원했으며 개선판 배포나 네이티브 영구 전환은 하지 않았다.

이번 장비에서는 **개선 Docker를 기본 선택지로 유지할 만하다.** 기존판 대비 유휴
PSS가 약 65.6MiB 줄었고, 네이티브의 추가 절감은 유휴 약 11.5MiB, 단일 페이지
약 6.0MiB였다. 큰 차이는 설치 방식보다 코드·상주 프로세스 개선에서 관찰됐다.
이는 아래 조건의 비교 결과이지 순수 Docker 오버헤드 측정이나 모든 사이트의 보장은 아니다.

## 재현 조건과 근거

- 장비: Raspberry Pi 4B 2GB, Debian 13 arm64, kernel `6.18.39+rpt-rpi-v8`.
- 기존판: `b7bd34b97d7391a1c691985c8e7714b8d493262e`.
- 개선판 실측 커밋: `3a172a12334378e958f4c84d4d944436b24d6442`.
  이후 문서 커밋을 이 실측 대상과 혼동하지 않는다.
- Chromium은 모두 `152.0.7977.82`. Python은 Docker `3.13.15`, 네이티브 `3.13.5`.
- browser 실행 집단: RAM 1GiB + swap 1GiB 상한. egress 96MiB, ingress 64MiB.
  Docker shared memory는 128MiB. 이는 Pi 전체 RAM이나 Docker 자체 소비량이 아니다.
- viewport 1024×768 CSS 픽셀, 가상 화면 상한 1920×1440.
- 같은 [Wikipedia 문서](https://en.wikipedia.org/wiki/World_Wide_Web), 새 시험 DB·프로필,
  관찰·viewport 캡처 각각 3회, 긴 관찰, 전체 페이지 캡처, 추가 탭 1개,
  시험용 수동 제어, 세션 종료를 같은 순서로 요청했다. 안정화 시간은 5초다.
- 기존 → 개선 Docker → 네이티브 순서를 3회 반복했다. OS 캐시는 비우지 않았고
  다른 MCP와 Docker daemon은 계속 실행했다. 데몬 메모리를 네이티브 절감에 포함하지 않았다.
- 수동 제어는 시험 작업의 handoff 시작·완료다. 실제 로그인·게시·구매를 수행하지 않았다.

[공개 수치 데이터](benchmarks/pi-2026-09-09.json)에는 9회 각각의 14개 단계별
PSS/RSS, browser cgroup raw/file cache, 호스트 여유·swap, 응답 시간, 오류와
memory.events 증분을 담았다. 값이 없는 `null`은 0이 아니다. RSS 합계는 공유 페이지가
중복 계산될 수 있다. 원본 초당 표본·배포 보존 영수증은 운영자가 비공개로 보관한다.
공개 자료에는 토큰·쿠키·환경변수·운영 프로필·원문 로그를 넣지 않았다.
새 실험에는 [동일 예산 비교 절차](PERFORMANCE_COMPARISON.md)를 사용한다.

## 메모리

browser + egress + ingress의 **PSS 합계, MiB**다. 각 실행의 단계별 중앙값을
구한 뒤 3회 중앙값을 냈다. 괄호는 그 세 값의 최소–최대이며 신뢰구간이 아니다.

| 단계 | 기존 Docker | 개선 Docker | 개선 네이티브 |
|---|---:|---:|---:|
| 유휴 | 256.40 (254.66–256.65) | 190.85 (190.84–190.86) | 179.34 (179.23–179.43) |
| 단일 무거운 페이지 | 920.93 (903.59–926.91) | 888.59 (875.76–893.11) | 882.55 (880.39–889.88) |
| 수동 제어 | 911.34 (900.51–918.82) | 929.42 (918.15–934.02) | 919.80 (918.36–927.95) |
| 세션 종료 후 | 322.85 (294.01–325.59) | 258.96 (252.33–259.68) | 243.24 (242.70–243.45) |

기존판 → 개선 Docker의 유휴 감소는 65.55MiB(25.6%)다. 개선 Docker → 네이티브는
유휴 11.51MiB, 단일 페이지 6.04MiB 감소다. 종료 후 값은 해당 안정화 구간의 관찰이며
장시간 후 최종 회수량을 뜻하지 않는다. raw charge에서 cache를 뺀 값만으로 절감을 주장하지 않는다.

기존판 1·2회차는 추가 탭을 거절했으므로 이후 수동 제어의 실제 작업량이 다르다.
이 구간에서 기존판의 PSS가 낮은 것을 성능 우위로 해석할 수 없다.

## 응답 시간

해당 실행·단계에 오류가 하나라도 있으면 그 단계의 호출을 제외한 **성공 표본 중앙값**이다.
표본 수가 다르므로 전체 작업 소요 시간이나 확정적인 속도 향상률로 일반화하지 않는다.

| 요청 | 기존 Docker | 개선 Docker | 개선 네이티브 |
|---|---:|---:|---:|
| 조작 요소 관찰 | 1010.5ms (n=6) | 808ms (n=9) | 765ms (n=9) |
| viewport 캡처 | 2180ms (n=6) | 1576ms (n=9) | 1590ms (n=9) |
| 긴 의미 기반 관찰 | 1084ms (n=2) | 1017ms (n=3) | 1004ms (n=3) |

네이티브가 개선 Docker보다 모든 요청에서 빠르지는 않았다. 공개 데이터에는 거절된
호출 시간도 남아 있으므로 집계할 때 `errors`의 해당 단계 여부를 함께 확인해야 한다.

## 실패와 실제 지원 범위

- 기존 Docker: `RESOURCE_PRESSURE` 12건(회차별 9/2/1). 요소 관찰 3건,
  viewport 캡처 3건, 긴 관찰 1건, 전체 페이지 캡처 3건, 추가 탭 2건이다.
- 개선 Docker와 네이티브: 각각 전체 페이지 캡처 `RESOURCE_PRESSURE` 3건.
  나머지 시험 요청과 세션 정리는 완료했다.
- **세 방식 모두 긴 문서 전체 페이지 캡처를 3/3회 거절했다.** 이 페이지와 1GiB
  예산에서 전체 페이지 캡처가 지원된다고 보고하지 않는다. 작은 viewport 캡처를 사용한다.
- 모든 실행·역할의 `oom`/`oom_kill` 증분은 0이다. 네이티브 첫 실행의 browser
  `memory.events:max`만 10 증가했다. 상한 도달/회수 기록이지 OOM kill이나 충돌은 아니다.
- 실시간 문서·네트워크, 캐시, 고정 실행 순서, Python 패치 버전 차이가 있다.
  한 장비·한 페이지·3회 결과에서 순수 컨테이너 비용이나 보편적 절감량을 분리할 수 없다.
- 이전 설치 권한·네트워크 문제로 중단된 두 비교 세트는 합치지 않았다.
- 이 측정은 웹 ChatGPT가 새 계약의 이미지를 실제 이해했음을 증명하지 않는다.
  사용자 연결에서의 [통합 검증](VALIDATION.md)은 별도다. Debian 13 amd64 현장 설치나
  Windows/macOS Docker 실측을 이번 Pi 결과로 대체하지 않는다.

## 시작 관문·회귀·운영 복원

측정 전 Debian 13 arm64 네이티브 설치와 서비스 계정 4개의 import, network → egress →
분리 ingress health → 인증된 MCP status를 확인했다. 약 18초 간격의 두 검사에서
전용 veth 주소·UP·NM unmanaged 상태, 동일 API 프로세스와 실제 1GiB RAM/swap 제한이
유지됐다. 유휴 상태에는 Chromium/Xvfb/VNC가 없었다. 기존 Docker와 다른 네트워크를
유지한 채 관문을 통과한 다음, 시험 역할을 정리하고 9회 비교를 시작했다.

실측 커밋의 [CI 34266596406](https://github.com/BK927/cloud-browser-mcp/actions/runs/34266596406)은
tests, docker-runtime, native-runtime, multiarch-build가 모두 성공했다.
Linux 테스트는 513 passed / 4 skipped이며 실제 Docker·systemd 네이티브 runtime과
격리된 NetworkManager 회귀, arm64/amd64 빌드를 포함한다. 로컬 전체 회귀는
509 passed / 8 skipped였다. CI와 실측은 서로 다른 증거다.

**2026-09-09 04:46:05 KST**, 배포 담당자가 기존 baseline으로 복원하고 원래 컨테이너·
이미지·설정·마운트·접속 경로의 동일성을 확인했다. 인증된 MCP 상태와 다른 MCP들의
health·인증 거부·OAuth 발견·대표 읽기 호출도 통과했다. 시험 Docker는 정지했고
네이티브 4개 unit은 비활성, 전용 시험 namespace는 제거됐다. 인증 DB·프로필을
백업본으로 덮어쓰지 않았으며 복구용 배포본·실패 이력은 보존했다.

개선 이미지와 네이티브 설치는 시험용으로 남겼다. 운영 업그레이드는 별도 결정이며
이 보고서나 공개 커밋은 자동 배포·네이티브 영구 전환·정식 버전 릴리스를 뜻하지 않는다.
