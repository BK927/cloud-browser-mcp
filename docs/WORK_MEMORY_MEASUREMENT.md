# 단독·동시 작업 메모리 측정

이 절차는 Docker/네이티브 전환이나 메모리 제한 증설이 아닙니다. 같은 후보 커밋,
같은 설치 방식, RAM 1024 MiB와 기존 별도 swap 한도를 유지한 상태에서 실행합니다.

## 실행 전 조건

- 배포 담당자가 정확한 후보 커밋의 CI와 복구용 배포본을 확인합니다.
- 사용자 작업이 정상 종료되어 `scheduler.active_sessions == 0`이고 수동 제어/인증이
  진행 중이 아닌 조용한 시간이어야 합니다. 다른 작업을 닫거나 회수하지 않습니다.
- 운영 비밀번호/OAuth 연결/원래 프로필/접속 경로/다른 MCP를 변경하지 않습니다.
- Windows 등 **Pi 외부 PC**에서 클라이언트를 실행합니다. Pi 내부의 시험 클라이언트
  소비량을 브라우저 성능으로 오인하지 않기 위한 조건입니다.
- 이전 운영 시험과 같은 검증된 경로로 최대 5분의 별도 임시 인증을 발급합니다.
  인증 발급·TTL 검사·독립 finally 폐기는 배포 담당자의 보호된 시험 wrapper가 담당합니다.
  이 스크립트는 인증을 발급하거나 재설정하지 않습니다. 토큰은 stdin으로 전달하며
  명령행·로그·결과 파일에 넣지 않습니다.

## 측정 행렬

1. 같은 공개 읽기 전용 페이지, 1024×768, JPEG 75, 출력 30000자로 고정합니다.
2. `scripts/work_memory_probe.py`를 single/dual 각각 3번 실행합니다. 실행별로 별도의
   짧은 인증을 사용합니다. `--label`에는 정확한 커밋/설치 방식을, `--repeat`에는 1/2/3을 기록합니다.
3. 각 실행은 유휴 상태 → 작업 열기(dual이면 두 독립 작업) → 각 작업의 interactive,
   semantic, visual 관찰 → 자기 작업 종료 → 회수 상태를 측정합니다.
4. `scripts/sample_memory.py`를 Pi의 정확한 서비스 cgroup에 대해 2초 간격으로 병행합니다.
   실행 시간으로 합쳐 프로세스 PSS/RSS, swap, cgroup 사용량/파일 캐시/PSI,
   OOM·프로세스 한도 거부 증가와 호스트 MemAvailable을 함께 분석합니다.
5. cgroup `memory_peak`는 그룹 수명 전체의 최고값입니다. 기존 기록을 재설정하지 않으며,
   이번 구간의 샘플 최고값과 구분합니다. 순간 peak를 빠짐없이 잡았다고 주장하지 않습니다.

클라이언트는 다른 작업 수가 감지되거나 한도가 다르면 비교를 중단합니다. 새 작업·캡처
거절도 유효한 관측 결과이며 자동 반복하지 않습니다. 부분 open의 회수 핸들도 보관하고,
한 작업 정리에 실패해도 나머지 **자기가 만든 작업** 정리는 시도합니다. 인증 폐기는
클라이언트 성공 여부와 관계없이 외부 wrapper가 별도로 수행해야 합니다.
전송 중 open 결과가 소실되면 클라이언트만으로 회수를 증명할 수 없습니다. 배포 담당자가
해당 임시 인증 주체의 시험 작업만 확인해야 하며, 다른 작업은 종료하지 않습니다.

`completed`는 측정 절차 완료이지 메모리 누수가 없다는 보증이 아닙니다. `stopped`,
`cleanup_required`, `unverified_recovery` 결과를 성공한 측정에 섞지 않습니다.
측정 도중 작업 수가 같게 바뀌는 동시 사용은 카운터만으로 배제할 수 없으므로
운영자의 조용한 시간 확인도 필요합니다.

## 현재 결과

로컬 모의 시험만 준비되었습니다. Pi 실제 수치와 3회 비교 결과는 아직 없습니다.
기존에 다른 작업이 열린 상태의 600~1000 MiB 수치를 단일 SPA 사용량으로 재활용하지 않습니다.
